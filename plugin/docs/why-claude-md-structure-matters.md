# Why CLAUDE.md structure matters

The `clayworks-lite-template` ships a specific section ordering: **identity → memory routing → multi-model routing → self-improvement cycle → behavioral rules → communication → project context → hardware → inter-session coordination → custom extensions**. Section ordering is the lesson, not the section contents. This doc explains why.

## The model reads top-to-bottom and weights early rules more heavily

I rely on Claude Code delivering CLAUDE.md as context at the start of the conversation (as a message after the system prompt, not inside it), and I see Claude read it top to bottom like any other text. I've found that early content sets *frames* that color how Claude interprets later content, and that late content can refine but rarely overrides framing. Because it isn't the system prompt, I can't count on strict compliance, which gives me one more reason to make each rule specific and put the load-bearing ones first.

Concrete examples:

- A CLAUDE.md that starts with "you are persistent across sessions through memory systems" primes Claude to think of itself as a stateful agent before it sees any specific rule. Later behavioral instructions land on an agent that's already model-of-self-as-persistent.
- Conversely, a CLAUDE.md that starts with project conventions ("use snake_case for Python files") and later mentions identity will get implementation behavior shaped correctly but no consistent agent persona across sessions — the identity framing comes too late to bind.

The choice isn't "should CLAUDE.md have an identity section." It's "where does the identity section land in the read order." LITE puts it first.

## The chosen order, briefly justified

1. **Identity** — establishes the frame Claude operates within. Everything below is "given that you're this agent, here's what you do."
2. **Memory system routing** — second because memory is *how* the agent's identity persists. Without memory rules, identity drifts every session. With them, identity has somewhere to anchor between conversations.
3. **Multi-model routing** — third because once Claude knows what it is and where it remembers, *what other tools it can reach for* shapes how it works. (Optional section: many users won't have multi-model setups.)
4. **Self-improvement cycle** — fourth because this is the discipline that keeps everything above coherent over time. It's meta: rules for maintaining the rules.
5. **Behavioral rules** — fifth because the rules apply within the frame established by 1-4. "Ask before destructive actions" lands differently when Claude already knows what kind of agent it is and how it remembers state.
6. **Communication** — sixth because this is the surface (how Claude talks to the user). Lower priority than rules of conduct; rules of conduct dictate communication, not vice versa.
7. **Project context** — seventh because project-level facts are *scoped*; everything above is global to the agent. The agent's identity travels across projects; project context doesn't.
8. **Hardware** — eighth because hardware is the constraint surface. Knowing the GPU specs matters less than knowing the working style.
9. **Inter-session coordination + Custom extensions** — last because they're advanced features users opt into. Putting them at the bottom signals "skip if you don't need this."

## Alternatives considered

**Behavioral rules first.** Read like a contract. Lands as instruction-following rather than agent-being. Claude defaults to "rule-follower with no persona" which is what generic CC stock gives you. Rejected because LITE specifically aims to put a coherent agent persona in front of Claude.

**Project context first.** Common in `CLAUDE.md` files generated by `/init`. Treats Claude like a project-specific tool: "this project uses Python 3.11, use snake_case." Loses the agent identity entirely. Works for single-project usage but breaks when the same Claude works across multiple projects and the agent identity is what should persist.

**Alphabetical ordering of sections.** Tempting for maintainability. Rejected because section ordering is the load-bearing design choice; sorting alphabetically would optimize for the maintainer's brain at the cost of the model's read order.

**Single-section CLAUDE.md (no section headers).** Simplest. Often what beginners write. Rejected because Claude (and humans editing the file) need section landmarks to update behavior in one area without re-litigating others. A `## Behavioral Rules` section means a contributor adding rule #9 doesn't have to re-read the identity section to know where it goes.

## Trade-offs accepted

- **Verbosity.** The template is ~150 lines. A minimalist alternative with no sections would be 50. Accepted: the cost of 100 lines is much smaller than the cost of behavioral drift over months.
- **Some sections feel optional.** Hardware, inter-session coordination, custom extensions — users without those will skim. Accepted: clear opt-out (the HTML comments say so explicitly) is better than absence (users who later want them have nowhere to anchor).
- **Section ordering can't be changed without thinking.** A future user who moves "behavioral rules" before "identity" will see a real behavior shift. Accepted: the constraint is documented in the template comments and in this doc.

## When this design would be wrong

- **You don't want an agent persona.** If Claude-as-rule-follower is exactly what you want, putting identity first is overkill. Strip the identity section and treat the file as a list of conventions. Several LITE-adjacent operator setups do this — they're not wrong, they're targeting a different use.
- **Many CLAUDE.md-like files per subdirectory in your project.** I don't have project-scoped files at `<project>/.claude/CLAUDE.md` try to establish identity — I leave that to the user-level `~/.claude/CLAUDE.md`. I apply the template's identity-first ordering to the user-level file, and I lead per-project files with project context, by design. I treat a repo that already keeps its instructions in `AGENTS.md` the same way: since 2.1.277, Claude Code reads `AGENTS.md` when a project has no `CLAUDE.md`, and I still get the user-level file loaded alongside it.
- **You're maintaining a multi-user team CLAUDE.md.** Team-shared files can't establish a single user's identity. They should lead with shared conventions, not single-operator persona. Use this template for personal use; write a different template for team use.

## Maintenance discipline

The template ships with HTML-comment guidance:

> Maintenance discipline:
> - Re-read this file monthly. If a rule hasn't fired in 90 days, consider removing it. CLAUDE.md drift is the #1 cause of "CC stopped behaving how I configured it."
> - When you add a new rule, write WHY in a comment next to it. Future-you will not remember the reasoning.

I made this part of the design, not an afterthought. I treat the ordering as load-bearing *and I know the file degrades over time without active maintenance*. I take both as real, and I address both. I suggest the `claude-md-management` plugin (`/claude-md-management:revise-claude-md`, `/claude-md-management:claude-md-improver`) as the maintenance tool — not because I see it as the only option, but because I found it's the option that exists.

## What this doc is NOT

- **Not a substitute for the template file itself** — `templates/CLAUDE.md.clayworks-template` carries the actual section headers + inline HTML comments. This doc explains why those headers are in that order.
- **Not academic prose** — the design choices are pragmatic, not theoretical. The "why" is "we tried other orderings and this one worked best" more than it is any deep model-architecture claim.
