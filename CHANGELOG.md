## [1.1.0] — 2026-09-22

Claude Code catch-up release. I watched Claude Code move from roughly 2.1.178 to 2.1.280 since my last substantive pass, and I found that a lot of what I'd said about hooks, plugins, and memory had drifted. I re-checked every claim against the current docs and a live 2.1.280 install. The headline change: I now wire the Nudge hook through the plugin install, so you get reminders with no `settings.json` editing.

With this release I also ship the work I landed after 1.0.1 without a tag. I landed the ICP-pivot work on 2026-05-19 and repositioned LITE for the actual customer profile (non-coder builders who want to ship real things with Claude Code) rather than the gatekept "technical operators" framing I shipped at v1.0.1. I didn't change the product; I changed the voice, framing, and audience filter. I shipped companion landing-page work in parallel at `clayboicardi-com`.

### Added

- **Plugin hook for Nudge.** I added `plugin/hooks/hooks.json` to register the UserPromptSubmit check, so I surface due reminders out of the box on a plugin install (`/plugin install clayworks-lite@clayworks-lite`). I rely on Claude Code auto-discovering `hooks/hooks.json`, so I don't declare it in `plugin.json`. I verified the hook fires under `claude --plugin-dir` on Windows (Git Bash) with 2.1.280.
- **`run-python.sh` launcher** in the Nudge skill's `scripts/`. I know Claude Code runs hook commands under bash on macOS/Linux and Git Bash on Windows, and I've seen many Windows machines with `python` or `py` but no `python3`. I wrote the launcher to try `python3`, then `python`, then `py -3` (probing each, since the Windows Store `python3` alias only prints a hint), and to exit 0 with no output when no Python exists, so I never let an optional feature turn every prompt into a hook error. I use it on both install paths: I call it through `${CLAUDE_PLUGIN_ROOT}` in the plugin hook and from `~/.claude/skills/` in the settings snippet.
- **`nudge_db.py`**, a small shared helper I wrote to resolve the alerts DB path, create its directory, run the one-time legacy migration, and own the schema. I have each script set `sys.dont_write_bytecode` before importing it, so I never leave a `__pycache__` in the skill directory (I hash that directory in the installers to spot your edits).
- **`CLAYWORKS_NUDGE_DB`** environment variable. I added it so you can put the alerts DB anywhere you like. I make the default honor `CLAUDE_CONFIG_DIR` when you set it.
- **CI:** I added a `plugin-validate` job that installs Claude Code from npm and runs `claude plugin validate --strict` on `./plugin`, `.`, and `./plugin/skills` (I need no login for it), and a `nudge-scripts` job on ubuntu and windows that syntax-checks the scripts, then runs add → check → ack → check through the exact command string in `hooks.json`, asserts no `__pycache__` appears, and confirms the launcher exits 0 silently with no Python on PATH. I now also run ShellCheck on `plugin/examples/full/hooks/*.sh` and the launcher. I made both installer jobs fail if an idempotent re-run reinstalls anything.
- **`--verify` / `-Verify`:** I now check the Nudge launcher and helper files there, and I gave them a `skip` status.
- **README hero banner.** I shipped the real Clayworks brand banner (locked Wedge Notch C symbol + sentence-case wordmark) at the top of `README.md` via a `<picture>` element. I delivered two variants (light + dark) in two formats (WebP primary at ~11 KB, PNG fallback at ~85-113 KB) and wired them with `prefers-color-scheme`, so I auto-switch the banner when a viewer toggles GitHub theme. I kept the light PNG as the ultimate fallback for ancient browsers without `<picture>` support.
- **Shipped-file manifest for uninstall.** I added `tools/gen-shipped-hashes.py` to walk main's history (plus release tags) and the working tree and write `.installer/shipped-hashes.txt`: every file any LITE version on main installed, with its sha256 (plus the CRLF variant for files a Windows checkout converts). I have CI regenerate it and fail if it's stale, and run an upgrade-uninstall test (in which I uninstall a v1.0.1 install with this release) on ubuntu, macOS, and Windows under pwsh and Windows PowerShell 5.1.

### Fixed

- **I fixed `--uninstall` / `-Uninstall` skipping every item of an older install.** I had both uninstallers compare installed files only against the current release, so after you pulled 1.1.0 every 1.0.x artifact looked "customized" and stayed put, while the run still said "Uninstall complete." I now have them also remove an item when every file in it matches some shipped version in the manifest (ignoring the `__pycache__` 1.0.x left behind), move a legacy Nudge DB out of the skill dir before checking it, and end with "Uninstall finished; I kept N item(s)" when they keep anything.
- **I stopped Nudge losing reminders across upgrades.** With a script install into a custom `--claude-dir`, I put the DB under that dir while the scripts read `~/.claude`; and my one-shot move could pick one legacy store and drop the rest, or give up for good after a transient lock. I changed the scripts to derive the install root from their own location (the `clayworks-lite/` dir the installer creates, or the plugin cache layout) and, every time they open the DB, to merge in every legacy store they find inside that root: the installers' `nudge-import/` drops, an `alerts.db` next to the scripts, and the script-install skill dir. I don't scan old plugin-cache versions: I never got 1.0.x Nudge working from a plugin install (I pointed its commands at `~/.claude/skills/...`), so I know no 1.0.x plugin cache holds reminders. I record each legacy row I've copied in a `merged_rows` ledger, keyed by row id and content rather than by the path it came from, so I never duplicate a row on a rerun, I never import twice a store an installer relocates after I merged it in place, I keep reminders with the same text created at different times separate, and I still bring across a legacy file an old 1.0.x process recreates after the merge. If another process is writing the stable DB, I wait about a second once and leave the rest of the merge for the next prompt, so I keep the hook well inside its timeout. I read each source through its own connection before writing, so if I fail writing the stable DB (disk full, read-only), I leave the source in place for the next run instead of blaming it. I open that connection read-write, though I only ever read from it: a store that crashed mid-write carries a hot rollback journal, and I need SQLite to roll it back before I can read the committed alerts. When I rename a store aside, I move its `-journal`, `-wal`, and `-shm` files with it. I leave a store that's only locked, silently, for the next run, and I open legacy stores with no lock wait so a locked one can't stall the hook; I leave one that fails for any other reason SQLite doesn't prove permanent (permissions, a disk I/O error, a read-only rollback) where it is and retry it, with a stderr line saying so; for a corrupt store, or one that isn't a Nudge DB, I print a one-line stderr diagnostic, and when LITE owns the file I rename it `*.unmergeable` (numbering the name rather than overwriting an earlier one) so I keep the data on disk and stop retrying. I have `nudge_db.py --list` and `--path` read the same store the hook reads, so I honor `CLAYWORKS_NUDGE_DB`, custom roots, and `CLAUDE_CONFIG_DIR` in the "view pending nudges" step.
- **I stopped the hook examples swallowing a malformed payload.** In each script's parser I now write a one-line diagnostic to stderr before falling back to defaults.
- **I keep an alert store inside the skill folder from vanishing on reinstall or uninstall.** When `CLAYWORKS_NUDGE_DB` points at any file in the Nudge skill folder (the legacy `scripts/alerts.db` or a custom name), I now move that file and its `-wal`/`-shm` siblings into `<root>/clayworks-lite/nudge/nudge-import/` in both installers before I replace or remove the folder, and I warn you to point the override elsewhere. On uninstall I move it only when I actually remove the folder.
- **I treat a whitespace-only `CLAYWORKS_NUDGE_DB` as unset in the installers too.** I already trimmed it in the runtime; in the installers I treated it as a relative path and dropped legacy alerts into a `nudge-import/` under your working directory, where I never looked at runtime.
- **I carry an acknowledgment made later in a retained legacy store over to the merged copy.** I record in the ledger which stable row each legacy row became, so when a 1.0.x install you kept acknowledges a reminder after the merge, I mark the copy acknowledged too and stop firing it. I never un-acknowledge a copy.
- **I refuse a symlinked install path.** If `<root>/hooks`, `hooks/examples`, either root template, the backup folder, any LITE skill folder, `<root>/clayworks-lite`, its `nudge/` folder, `nudge-import/`, the `alerts.db` file itself (or its SQLite sidecars), `<root>/skills`, the Nudge skill folder, its `scripts/`, or a legacy store in it (plus sidecars) is a symlink or junction, I stop both installers with an error before reading, moving, or writing anything, so I never land reminders outside the Claude directory you chose, and I never move a database out of a folder the link points at.
- **I keep a moved alert store's SQLite journal with it.** When I move a store in the installers, I carry its `-journal` file along with `-wal`/`-shm`, so I can still recover a store caught mid-write cleanly.
- **I name your actual Claude directory in the next-steps text.** With `--claude-dir`, I used to point the setup instructions at `~/.claude`; I now print the directory you chose, quoted for your shell.
- **I made a Windows-style `CLAYWORKS_NUDGE_DB` work under Git Bash.** In `install.sh` I passed `C:\Users\me\alerts.db` to POSIX `dirname`, which can't split on backslashes, so I put `nudge-import/` in your current directory while I had Nudge looking next to the real file. I now convert the path with `cygpath` first.
- **I refuse a `~user` override instead of misplacing your alerts.** I know Python expands `~alice/alerts.db` to Alice's home, which I couldn't match in the installers on every platform, so I put `nudge-import/` under a literal `~alice` folder I never scan at runtime. I now stop both installers with a clear error and ask for a full path.
- **I make the alerts DB owner-only before any reminder lands in it.** I used to tighten it to 0600 after merging legacy stores, so I left a new DB in a shared folder at the umask's permissions while rows went in. I now create it as 0600 (and strip group and other access from an existing one, without ever adding a permission) before the merge.
- **I never let a merge strand a row an old process writes mid-merge.** For a legacy store I rename once merged, I hold an exclusive SQLite lock from the read through the rename on macOS and Linux, so an old 1.0.x process can't commit a row in between. I can't rename an open file on Windows, so there my rename fails while a writer still has the file open, and I pick up its new rows through the ledger on the next run.
- **I keep a skill that holds a `.pyc` you added on uninstall.** I ignored `*.pyc` anywhere in the shipped-version check, so I removed the folder on uninstall even with a custom `.pyc` beside a `SKILL.md`. I now ignore only files inside a `__pycache__/` folder.
- **I keep a skill that holds a link you added on uninstall.** I skipped symlinks in the hash comparison, so I removed an otherwise unchanged skill folder on uninstall, link and all. I now treat any folder containing a symlink or junction as customized and keep it.
- **I refuse a `CLAYWORKS_NUDGE_DB` inside another folder I replace.** If the override points into a different LITE skill, `hooks/examples`, or a root template, I now stop install and uninstall with a clear error before touching anything; before, I moved the live store into the backup on a reinstall and started Nudge over empty. I keep the move-and-warn handling for the Nudge skill folder.
- **I refuse a symlinked default DB in the Nudge runtime too.** With a plugin install I run the scripts with no installer preflight, so a link at the default `alerts.db` (or its folder or a SQLite sidecar) would have had me chmod and write reminders through it. I now stop the scripts with an error that names the link; I leave a `CLAYWORKS_NUDGE_DB` you set yourself as your call.
- **I skip linked legacy stores and refuse Windows junctions in the Nudge runtime.** I now treat an NTFS junction like a symlink everywhere I check for links (`Path.is_symlink()` doesn't report junctions), and I never import a legacy `alerts.db` that is itself a link, has a linked sidecar, or sits behind a linked folder inside your Claude folder; I note the skip on stderr instead.
- **I quote paths safely in the printed purge commands.** With a Claude directory containing an apostrophe (`O'Brien`), I used to print broken, pasteable-but-wrong commands; I now use `printf %q` in the bash output and double apostrophes inside `-LiteralPath` arguments in the PowerShell output.
- **I run `ack_alert.py` through `run-python.sh` in the Nudge dismiss hint**, so I support Windows machines with only `python` or `py -3`; before, I repeated the alert on every prompt because `python3` didn't exist. I also shell-quote both paths in the hint, since Claude may run that line: I make sure an install path with quotes, `$`, or backticks can't break out of its argument.

### Security

- `install.sh` and `install.ps1`: refuse to install if the source tree contains symlinks or (on Windows) junctions. A tampered clone — typosquatted fork, malicious PR merged, MITM on `git clone` — could include a symlink at e.g. `skills/clayworks-lite-evil/exfil -> ~/.ssh/id_ed25519`. Under the previous `cp -R` / `Copy-Item -Recurse`, the symlink was followed and the target's *contents* were written as a real file into `~/.claude/skills/...` — a predictable, user-readable exfil channel that any later malicious skill, hook, sync process, or backup tool could read. The check is fail-loud: the installer prints the offending paths and exits with code 4. Honest LITE source trees contain no symlinks, so the check is invisible to non-malicious users. Defense-in-depth: `install.sh` now also uses `cp -RP` (no-dereference) and `path_hash()` excludes symlinks from the directory walk so the hash is deterministic against TOCTOU.
- `hooks/examples/sessionstart.sh`: neutralized the most common git-config-based arbitrary-command-execution vectors (CVE-2022-39253 family) when the example invokes `git status` in user-controlled cwd. Replaced `cd "$CWD" && git status` with `git -C "$CWD" -c core.fsmonitor=false -c core.hooksPath=/dev/null status` plus `GIT_OPTIONAL_LOCKS=0`. Added a SECURITY comment explaining the residual risk (hook-based vectors in `.git/hooks/` are NOT fully addressed and remain a concern if users open CC inside untrusted repos). Also added a SECURITY comment above the primer-file injection block warning that `$PRIMER`'s path is security-sensitive (any process that can write to it can inject instructions into the next CC session via the system-reminder channel).
- `hooks/examples/stop.sh`: added a SECURITY comment above the gated 24h-trigger background-job pattern warning that the script path is security-sensitive — anything that can write to the pinned path gets `nohup bash` execution on every Stop. Recommended chmod 700 on the dir and the script.
