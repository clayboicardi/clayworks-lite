## [1.1.0] — 2026-09-22

Claude Code catch-up release. Claude Code moved from roughly 2.1.178 to 2.1.280 since my last substantive pass, and a lot of what LITE said about hooks, plugins, and memory had drifted. I re-checked every claim against the current docs and a live 2.1.280 install. The headline change: the plugin install now wires the Nudge hook for you, so reminders fire with no `settings.json` editing.

This release also ships the work that landed after 1.0.1 without a tag. I landed the ICP-pivot work on 2026-05-19 and repositioned LITE for the actual customer profile (non-coder builders who want to ship real things with Claude Code) rather than the gatekept "technical operators" framing I shipped at v1.0.1. I didn't change the product; I changed the voice, framing, and audience filter. I shipped companion landing-page work in parallel at `clayboicardi-com`.

### Added

- **Plugin hook for Nudge.** I added `plugin/hooks/hooks.json` to register the UserPromptSubmit check, so a plugin install (`/plugin install clayworks-lite@clayworks-lite`) surfaces due reminders out of the box. Claude Code auto-discovers `hooks/hooks.json`, so I don't declare it in `plugin.json`. I verified the hook fires under `claude --plugin-dir` on Windows (Git Bash) with 2.1.280.
- **`run-python.sh` launcher** in the Nudge skill's `scripts/`. Hook commands run under bash on macOS/Linux and Git Bash on Windows, and many Windows machines have `python` or `py` but no `python3`. I wrote the launcher to try `python3`, then `python`, then `py -3` (probing each, since the Windows Store `python3` alias only prints a hint), and to exit 0 with no output when no Python exists, so an optional feature never turns every prompt into a hook error. I use it on both install paths: the plugin hook calls it through `${CLAUDE_PLUGIN_ROOT}`, and the settings snippet calls it from `~/.claude/skills/`.
- **`nudge_db.py`**, a small shared helper I wrote that resolves the alerts DB path, creates its directory, runs the one-time legacy migration, and owns the schema. Each script sets `sys.dont_write_bytecode` before importing it, so no `__pycache__` lands in the skill directory (the installers hash that directory to spot your edits).
- **`CLAYWORKS_NUDGE_DB`** environment variable, so you can put the alerts DB anywhere you like. The default honors `CLAUDE_CONFIG_DIR` when you set it.
- **CI:** I added a `plugin-validate` job that installs Claude Code from npm and runs `claude plugin validate --strict` on `./plugin`, `.`, and `./plugin/skills` (it needs no login), and a `nudge-scripts` job on ubuntu and windows that syntax-checks the scripts, then runs add → check → ack → check through the exact command string in `hooks.json`, asserts no `__pycache__` appears, and confirms the launcher exits 0 silently with no Python on PATH. ShellCheck now also covers `plugin/examples/full/hooks/*.sh` and the launcher. Both installer jobs now fail if an idempotent re-run reinstalls anything.
- **`--verify` / `-Verify`** now check the Nudge launcher and helper files, and I gave them a `skip` status.
- **README hero banner.** I shipped the real Clayworks brand banner (locked Wedge Notch C symbol + sentence-case wordmark) at the top of `README.md` via a `<picture>` element. I delivered two variants (light + dark) in two formats (WebP primary at ~11 KB, PNG fallback at ~85-113 KB) and wired them with `prefers-color-scheme`, so the banner auto-switches when a viewer toggles GitHub theme. The light PNG is the ultimate fallback for ancient browsers without `<picture>` support.
- **Shipped-file manifest for uninstall.** I added `tools/gen-shipped-hashes.py`, which walks main's history (plus release tags) and the working tree, and writes `.installer/shipped-hashes.txt`: every file any LITE version on main installed, with its sha256 (plus the CRLF variant for files a Windows checkout converts). CI regenerates it and fails if it's stale, and runs an upgrade-uninstall test (in which this release uninstalls a v1.0.1 install) on ubuntu, macOS, and Windows under pwsh and Windows PowerShell 5.1.

### Fixed

- **`--uninstall` / `-Uninstall` skipped every item of an older install.** Both uninstallers compared installed files only against the current release, so after you pulled 1.1.0 every 1.0.x artifact looked "customized" and stayed put, while the run still said "Uninstall complete." They now also remove an item when every file in it matches some shipped version in the manifest (ignoring the `__pycache__` 1.0.x left behind), move a legacy Nudge DB out of the skill dir before checking it, and end with "Uninstall finished; N item(s) kept" when they keep anything.
- **Nudge could lose reminders across upgrades.** A script install into a custom `--claude-dir` put the DB under that dir while the scripts read `~/.claude`; and a one-shot move could pick one legacy store and drop the rest, or give up for good after a transient lock. I changed the scripts to derive the install root from their own location (the `clayworks-lite/` dir the installer creates, or the plugin cache layout) and, every time they open the DB, to merge in every legacy store they find inside that root: the installers' `nudge-import/` drops, an `alerts.db` next to the scripts, and the script-install skill dir. I don't scan old plugin-cache versions: 1.0.x Nudge never worked from a plugin install (its commands pointed at `~/.claude/skills/...`), so no 1.0.x plugin cache holds reminders. A `merged_rows` ledger records each legacy row I've copied, keyed by row id and content rather than by the path it came from, so reruns never duplicate a row, a store an installer relocates after I merged it in place isn't imported twice, reminders with the same text created at different times stay separate, and a legacy file an old 1.0.x process recreates after the merge still comes across. If another process is writing the stable DB, I wait about a second once and leave the rest of the merge for the next prompt, so the hook stays well inside its timeout. I read each source through its own connection before writing, so a failure writing the stable DB (disk full, read-only) leaves the source in place for the next run instead of blaming it. That connection is read-write, though I only ever read from it: a store that crashed mid-write carries a hot rollback journal, and SQLite has to roll it back before it can read the committed alerts. When I rename a store aside, its `-journal`, `-wal`, and `-shm` files move with it. A store that's only locked waits silently for the next run, and I open legacy stores with no lock wait so a locked one can't stall the hook; one that fails for any other reason SQLite doesn't prove permanent (permissions, a disk I/O error, a read-only rollback) stays where it is and retries, with a stderr line saying so; a corrupt store, or one that isn't a Nudge DB, gets a one-line stderr diagnostic, and when LITE owns the file I rename it `*.unmergeable` (numbering the name rather than overwriting an earlier one) so the data stays on disk and I stop retrying. `nudge_db.py --list` and `--path` read the same store the hook reads, so the "view pending nudges" step honors `CLAYWORKS_NUDGE_DB`, custom roots, and `CLAUDE_CONFIG_DIR`.
- **Hook examples no longer swallow a malformed payload.** Each script's parser writes a one-line diagnostic to stderr before falling back to defaults.
- **An alert store inside the skill folder no longer vanishes on reinstall or uninstall.** When `CLAYWORKS_NUDGE_DB` points at any file in the Nudge skill folder (the legacy `scripts/alerts.db` or a custom name), both installers now move that file and its `-wal`/`-shm` siblings into `<root>/clayworks-lite/nudge/nudge-import/` before they replace or remove the folder, and warn you to point the override elsewhere. Uninstall moves it only when it actually removes the folder.
- **A whitespace-only `CLAYWORKS_NUDGE_DB` counts as unset in the installers too.** The runtime already trimmed it; the installers treated it as a relative path and dropped legacy alerts into a `nudge-import/` under your working directory, where the runtime never looked.
- **An acknowledgment made later in a retained legacy store reaches the merged copy.** The ledger records which stable row each legacy row became, so when a 1.0.x install you kept acknowledges a reminder after the merge, I mark the copy acknowledged too and it stops firing. I never un-acknowledge a copy.
- **I refuse a symlinked install path.** If `<root>/hooks`, `hooks/examples`, either root template, the backup folder, any LITE skill folder, `<root>/clayworks-lite`, its `nudge/` folder, `nudge-import/`, the `alerts.db` file itself (or its SQLite sidecars), `<root>/skills`, the Nudge skill folder, its `scripts/`, or a legacy store in it (plus sidecars) is a symlink or junction, both installers stop with an error before reading, moving, or writing anything, so reminders can't land outside the Claude directory you chose, and I never move a database out of a folder the link points at.
- **A moved alert store keeps its SQLite journal.** When the installers move a store, they carry its `-journal` file along with `-wal`/`-shm`, so a store caught mid-write still recovers cleanly.
- **The next-steps text names your actual Claude directory.** With `--claude-dir`, the setup instructions used to point at `~/.claude`; they now print the directory you chose, quoted for your shell.
- **A Windows-style `CLAYWORKS_NUDGE_DB` works under Git Bash.** `install.sh` passed `C:\Users\me\alerts.db` to POSIX `dirname`, which can't split on backslashes, so it put `nudge-import/` in your current directory while Nudge looked next to the real file. I now convert the path with `cygpath` first.
- **I refuse a `~user` override instead of misplacing your alerts.** Python expands `~alice/alerts.db` to Alice's home, which the installers couldn't match on every platform, so they put `nudge-import/` under a literal `~alice` folder the runtime never scans. Both installers now stop with a clear error and ask for a full path.
- **The alerts DB is owner-only before any reminder lands in it.** I used to tighten it to 0600 after merging legacy stores, so a new DB in a shared folder sat at the umask's permissions while rows went in. I now create it as 0600 (and strip group and other access from an existing one, without ever adding a permission) before the merge.
- **A merge can't strand a row an old process writes mid-merge.** For a legacy store I rename once merged, I hold an exclusive SQLite lock from the read through the rename on macOS and Linux, so an old 1.0.x process can't commit a row in between. Windows won't rename an open file, so there a writer that still has it open makes the rename fail, and the ledger picks up its new rows on the next run.
- **Uninstall keeps a skill that holds a `.pyc` you added.** The shipped-version check ignored `*.pyc` anywhere, so a custom `.pyc` beside a `SKILL.md` let uninstall remove the folder. I now ignore only files inside a `__pycache__/` folder.
- **Uninstall keeps a skill that holds a link you added.** The hash comparison skipped symlinks, so a link inside an otherwise unchanged skill let uninstall remove the folder, link and all. I now treat any folder containing a symlink or junction as customized and keep it.
- **I refuse a `CLAYWORKS_NUDGE_DB` inside another folder I replace.** If the override points into a different LITE skill, `hooks/examples`, or a root template, install and uninstall now stop with a clear error before touching anything; before, a reinstall moved the live store into the backup and Nudge started over empty. The Nudge skill folder keeps its move-and-warn handling.
- **The Nudge runtime refuses a symlinked default DB too.** A plugin install runs the scripts with no installer preflight, so a link at the default `alerts.db` (or its folder or a SQLite sidecar) would have had me chmod and write reminders through it. The scripts now stop with an error that names the link; a `CLAYWORKS_NUDGE_DB` you set yourself stays your call.
- **The printed purge commands quote paths safely.** A Claude directory with an apostrophe (`O'Brien`) used to produce broken, pasteable-but-wrong commands; bash output now uses `printf %q` and PowerShell output doubles apostrophes inside `-LiteralPath` arguments.
- **The Nudge dismiss hint** now runs `ack_alert.py` through `run-python.sh`, so it works on Windows machines with only `python` or `py -3`; before, the alert repeated on every prompt because `python3` didn't exist. I also shell-quote both paths in the hint, since Claude may run that line: an install path with quotes, `$`, or backticks can't break out of its argument.
- **`install.sh` no longer runs `chmod 700` on a directory it didn't create**, so pointing `CLAYWORKS_NUDGE_DB` into an existing shared directory leaves that directory's permissions alone.
- **`install.sh --verify` failed on machines without a `python3` executable** even with Python installed, reporting "settings.example.json: present but JSON parse failed." Both installers now look for `python3`, `python`, then `py -3`; a missing Python is a warning (Python is optional), and the bash JSON check reports a skip instead of a failure when no Python exists.
- **`install.sh` re-installed unchanged files when `--claude-dir` held a backslash** (a Windows-style path under Git Bash). GNU `sha256sum` prefixes its output with `\` for such paths, so the hashes never matched and every re-run backed up and re-copied the templates. `sha_file` now reads the file on stdin.
- **`install.ps1` re-installed unchanged directories when `-ClaudeDir` used an 8.3 short path** such as the default `%TEMP%` (`C:\Users\RUNNER~1\...`). `Get-ChildItem` expands short names, so slicing `FullName` by the root's length produced wrong relative paths and wrong hashes. The same bug made `-Uninstall` skip every skill as "customized." `Get-PathHash` now enumerates relative paths with `-Name`. CI had missed it because its idempotency check only required one unchanged item.
- **A reinstall could strand Nudge alerts.** Because `alerts.db` lived inside the skill folder, updating through the installer backed it up and removed it, and `--uninstall` skipped the Nudge skill as "customized." I moved the DB out of the skill folder, which fixes both.

### Security

- `install.sh` and `install.ps1`: refuse to install if the source tree contains symlinks or (on Windows) junctions. A tampered clone — typosquatted fork, malicious PR merged, MITM on `git clone` — could include a symlink at e.g. `skills/clayworks-lite-evil/exfil -> ~/.ssh/id_ed25519`. Under the previous `cp -R` / `Copy-Item -Recurse`, the symlink was followed and the target's *contents* were written as a real file into `~/.claude/skills/...` — a predictable, user-readable exfil channel that any later malicious skill, hook, sync process, or backup tool could read. The check is fail-loud: the installer prints the offending paths and exits with code 4. Honest LITE source trees contain no symlinks, so the check is invisible to non-malicious users. Defense-in-depth: `install.sh` now also uses `cp -RP` (no-dereference) and `path_hash()` excludes symlinks from the directory walk so the hash is deterministic against TOCTOU.
- `hooks/examples/sessionstart.sh`: neutralized the most common git-config-based arbitrary-command-execution vectors (CVE-2022-39253 family) when the example invokes `git status` in user-controlled cwd. Replaced `cd "$CWD" && git status` with `git -C "$CWD" -c core.fsmonitor=false -c core.hooksPath=/dev/null status` plus `GIT_OPTIONAL_LOCKS=0`. Added a SECURITY comment explaining the residual risk (hook-based vectors in `.git/hooks/` are NOT fully addressed and remain a concern if users open CC inside untrusted repos). Also added a SECURITY comment above the primer-file injection block warning that `$PRIMER`'s path is security-sensitive (any process that can write to it can inject instructions into the next CC session via the system-reminder channel).
- `hooks/examples/stop.sh`: added a SECURITY comment above the gated 24h-trigger background-job pattern warning that the script path is security-sensitive — anything that can write to the pinned path gets `nohup bash` execution on every Stop. Recommended chmod 700 on the dir and the script.
